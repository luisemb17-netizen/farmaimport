El sistema

Cuatro módulos que cubren todo el ciclo

Del registro del empleado a la factura impresa y el reporte del día.

1

Autenticación y usuarios

Registro con metadatos, dos roles y alta de cuentas desde el panel.

  • Trigger que crea el perfil al registrarse
  • Trigger que impide escalar privilegios
  • El admin crea cajeros con su clave
2

Productos e inventario

CRUD completo, categorías, imágenes en Storage y control de existencias.

  • Búsqueda y paginación (10 por página)
  • Aviso de stock bajo (≤ 5) y agotado
  • Un producto vendido se desactiva, no se borra

Punto de venta

Caja rápida con carrito lateral, cliente por cédula o RIF y cuatro métodos de pago.

  • El precio sale de la base, nunca del navegador
  • Descuento de stock y numeración segura
4

Facturación y reportes

Factura con formato SENIAT, PDF, impresión, anulación y tablero de indicadores.

  • Número de factura y de control consecutivos
  • Base imponible, exento (E), IVA y total en Bs.
  • Reportes en hora de Venezuela y top 5

Snapshots: la factura nunca cambia

En detalle_ventas se copian el nombre y el precio del producto; en ventas, el nombre, RIF y dirección del cliente.

Una sola fila de configuración

Un índice único sobre una constante (((true))) impide una segunda fila con datos fiscales contradictorios.

Consecutivos sin huecos

Las secuencias viven en esa fila única. La función las bloquea con FOR UPDATE, así que dos cajas nunca sacan el mismo número.

Integridad: no se borra lo que ya se vendió

detalle_ventas usa ON DELETE RESTRICT. Si intentas borrar un producto con ventas, PostgreSQL responde 23503.

Seguridad

Tres barreras: RLS, funciones y triggers

Ocultar un enlace en el menú no protege nada: la última barrera está en la base de datos.

1

Row Level Security

Todas las tablas tienen RLS activo. Cada consulta se filtra por auth.uid().

  • El cajero solo ve sus ventas
  • El administrador ve todas
  • Ventas y detalle no tienen política de escritura
2

es_admin()

Función SECURITY DEFINER que responde: ¿el usuario actual es administrador activo?

  • Evita la recursión infinita del RLS
  • Se ejecuta con permisos del dueño
  • Se usa dentro de las políticas
3

proteger_rol()

Trigger que impide que un cajero cambie su rol o su estado.

  • Compara OLD y NEW
  • Si no es admin, lanza excepción
  • Desde el SQL Editor no bloquea
Probado en producción: un cajero que escriba /dashboard/usuarios es redirigido, y si llamara la API directamente el RLS le devuelve solo su información.

-- 006_crear_usuario.sql (extracto) -- 1) La barrera: se valida DENTRO de PostgreSQL if not public.es_admin() then raise exception 'Solo un administrador puede crear usuarios'; end if; -- 2) Cuenta de autenticación con la clave hasheada (bcrypt) insert into auth.users (id, email, encrypted_password, email_confirmed_at, ...) values (v_id, v_email, crypt(p_password, gen_salt('bf')), now(), ...); -- 3) Identidad: sin esta fila el login por correo falla insert into auth.identities (user_id, provider_id, provider, identity_data) values (v_id, v_id::text, 'email', jsonb_build_object('sub', v_id::text, 'email', v_email));
Por qué así: la Admin API de Supabase exige la service_role key, que jamás debe estar en la aplicación. Con una función SECURITY DEFINER el permiso se valida en la base y no hay llaves secretas en el frontend.

Flujo de una venta

Del clic en «Cobrar» hasta la factura: una sola transacción atómica

El código

registrar_venta(): el corazón del sistema

Una función PL/pgSQL que o hace todo, o no hace nada.

-- 003_modulo3.sql create or replace function public.registrar_venta( p_cliente_id uuid, p_metodo_pago text, p_items jsonb, ... ) returns uuid language plpgsql security definer set search_path = public as $$ begin -- 1) Bloquea la configuración (secuencias seguras) select * into v_cfg from configuracion_negocio limit 1 for update; -- 2) Cabecera con números consecutivos insert into ventas (numero_factura, numero_control, ...) values ('FAC-' || lpad(v_cfg.secuencia_factura::text, 6, '0'), '00-' || lpad(v_cfg.secuencia_control::text, 6, '0'), ...); -- 3) Por ítem: bloquea, valida y descuenta for v_item in select * from jsonb_array_elements(p_items) loop select * into v_prod from productos where id = (v_item->>'producto_id')::uuid and activo for update; if v_prod.stock < v_cant then raise exception 'Stock insuficiente para %', v_prod.nombre; end if; update productos set stock = stock - v_cant ...; insert into detalle_ventas (... nombre, precio ...); end loop; -- 4) IVA y totales: aquí, no en el navegador v_iva := round(v_gravado * v_cfg.porcentaje_iva / 100, 2); update ventas set subtotal = v_gravado, monto_iva = v_iva, total = v_gravado + v_exento + v_iva; return v_venta_id; end; $$;

FOR UPDATE

Bloquea la fila mientras dura la transacción. La segunda caja espera y recibe el número siguiente.

SECURITY DEFINER

Corre con permisos del dueño: puede escribir donde el usuario no. Solo ella y anular_venta() tocan las ventas.

Precio desde la base

El navegador envía cantidades; el precio se lee del producto. No se puede "cambiar" desde la consola.

Redondeo a 2 decimales

Cada línea se redondea y el IVA se calcula sobre la base. La pantalla usa la misma regla.

Server Components por defecto

Listas, detalle y reportes se leen en el servidor. Solo el carrito, formularios, gráficos y PDF son cliente.

Un esquema Zod, dos usos

El mismo esquema valida el formulario en el navegador y los datos en la Server Action.

La lógica no vive en el componente

Cálculos en lib/calculos.ts, formato en lib/formato.ts, validación en lib/validaciones/.

Zona horaria fija

Vercel corre en UTC. Todo se formatea con America/Caracas para que «ventas de hoy» no salga corrido 4 horas.
