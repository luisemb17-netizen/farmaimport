Criterio

Cuatro decisiones que resuelven problemas reales

Cada una responde a un error típico de los sistemas de facturación.

1

Snapshots en la factura

Al vender se copian el nombre, RIF y dirección del cliente, y el nombre y precio del producto.

  • Si mañana sube el precio, la factura de ayer no cambia
  • La factura histórica es inmutable por diseño
2

Una sola fila de configuración

Un índice único sobre una constante (((true))) hace imposible una segunda fila.

  • Un solo RIF, un solo IVA, una sola secuencia
  • No hay datos fiscales contradictorios
3

Nada se borra: se anula

Las facturas cambian de estado; los productos vendidos se desactivan.

  • ON DELETE RESTRICT en el detalle
  • PostgreSQL responde 23503 y la app ofrece desactivar
4

Dinero con decimal(12,2)

Nunca float: los montos se guardan como decimales exactos.

  • Redondeo a 2 decimales en cada línea
  • El IVA se calcula sobre la base imponible

Seguridad · parte 1

Row Level Security: cada fila decide quién la ve

13 políticas activas. Sin política, la tabla devuelve cero filas: el RLS cierra por defecto.

-- 003_modulo3.sql alter table public.ventas enable row level security; -- El cajero ve SOLO sus ventas; el admin ve todas create policy "ver ventas" on public.ventas for select to authenticated using (vendedor_id = auth.uid() or public.es_admin()); -- El detalle hereda la visibilidad de su venta create policy "ver detalle" on public.detalle_ventas for select to authenticated using (exists ( select 1 from public.ventas v where v.id = detalle_ventas.venta_id and (v.vendedor_id = auth.uid() or public.es_admin()) )); -- En perfiles, cada quien ve el suyo; el admin ve todos create policy "ver perfil propio o admin" on public.perfiles for select to authenticated using (id = auth.uid() or public.es_admin()); -- A propósito NO hay políticas de INSERT/UPDATE/DELETE -- en ventas ni en detalle_ventas: solo escriben las funciones.

Seguridad · parte 2

Dos funciones que sostienen todo el modelo

Una evita la recursión del RLS; la otra impide que un cajero se ascienda solo.

-- 001_modulo1.sql create or replace function public.es_admin() returns boolean language sql stable security definer set search_path = public as $$ select exists ( select 1 from public.perfiles where id = auth.uid() and rol = 'administrador' and activo ); $$;

¿Por qué SECURITY DEFINER?

Una política de perfiles que consulte perfiles vuelve a evaluar la misma política y Postgres responde infinite recursion detected in policy. Con SECURITY DEFINER la función corre con permisos del dueño, se salta el RLS y corta la recursión.

-- 001_modulo1.sql create or replace function public.proteger_rol() returns trigger language plpgsql security definer set search_path = public as $$ begin if auth.uid() is not null and not public.es_admin() and (new.rol is distinct from old.rol or new.activo is distinct from old.activo) then raise exception 'Solo un administrador puede cambiar el rol o el estado'; end if; return new; end; $$;

¿Qué protege?

Si un cajero edita su propio perfil y cambia rol = 'administrador', el trigger lo detiene antes de guardar. Desde el SQL Editor no bloquea porque auth.uid() es NULL (así se crea el primer admin).

Cómo se guarda una venta

Una sola transacción: o se guarda todo, o no se guarda nada

El código en uso · 1

registrar_venta(): la función más importante

Vive en la base de datos, no en el navegador. El frontend solo la llama.

-- 003_modulo3.sql create or replace function public.registrar_venta( p_cliente_id uuid, p_metodo_pago text, p_items jsonb ) returns uuid language plpgsql security definer set search_path = public as $$ begin select * into v_cfg from configuracion_negocio limit 1 for update; -- bloquea la fila insert into ventas (numero_factura, numero_control, ...) values ('FAC-' || lpad(v_cfg.secuencia_factura::text, 6, '0'), '00-' || lpad(v_cfg.secuencia_control::text, 6, '0'), ...); for v_item in select * from jsonb_array_elements(p_items) loop select * into v_prod from productos where id = (v_item->>'producto_id')::uuid and activo for update; -- bloquea el producto if v_prod.stock < v_cant then raise exception 'Stock insuficiente para %', v_prod.nombre; end if; update productos set stock = stock - v_cant ...; insert into detalle_ventas (... nombre, precio ...); -- snapshot end loop; v_iva := round(v_gravado * v_cfg.porcentaje_iva / 100, 2); update ventas set subtotal = v_gravado, monto_iva = v_iva, total = v_gravado + v_exento + v_iva; update configuracion_negocio set secuencia_factura = secuencia_factura + 1, secuencia_control = secuencia_control + 1; return v_venta_id; end; $$;

1 · FOR UPDATE evita números repetidos

Dos cajas que cobran al mismo tiempo no pueden leer la misma secuencia: la segunda espera a que la primera termine.

2 · El precio sale de la base

El navegador manda solo producto_id y cantidad. Si alguien altera el precio desde la consola, no sirve de nada.

3 · Todo o nada

Si un producto no tiene stock, se lanza una excepción y PostgreSQL revierte la venta completa: no queda stock descontado ni un número gastado.

4 · Redondeo controlado

Cada línea se redondea a 2 decimales y el IVA se calcula sobre la base imponible, igual que en lib/calculos.ts.

El código en uso · 2

Anular una factura y generar reportes

Anular no borra: cambia el estado, guarda autor y motivo, y devuelve el stock.

-- 004_modulo4.sql create or replace function public.anular_venta( p_venta_id uuid, p_motivo text ) returns void language plpgsql security definer set search_path = public as $$ begin if not public.es_admin() then raise exception 'Solo un administrador puede anular'; end if; update public.ventas set estado = 'anulada', anulada_por = auth.uid(), anulada_at = now(), motivo_anulacion = trim(p_motivo) where id = p_venta_id and estado = 'completada'; -- Devuelve el stock agrupando por producto update public.productos p set stock = p.stock + d.unidades from ( select producto_id, sum(cantidad) as unidades from public.detalle_ventas where venta_id = p_venta_id group by producto_id ) d where p.id = d.producto_id; end; $$;

Vista ventas_por_dia

Agrupa las ventas por día con AT TIME ZONE 'America/Caracas' y security_invoker = true, así respeta el RLS de quien consulta. Las anuladas no suman.

top_productos(desde, hasta)

Devuelve el top 5 por unidades vendidas en un rango, uniendo detalle y ventas y filtrando solo las completadas.

resumen_periodo(desde, hasta)

Totales del período: facturas, base imponible, exento, IVA y total. Excluye las anuladas.

Por qué se agrupa el stock

Si un producto aparece en dos líneas de la misma factura, se suman las unidades antes de devolverlas; si no, se devolvería de menos.

El código en uso · 3

crear_usuario(): alta de cuentas sin llaves secretas

La Admin API de Supabase exige la service_role key. Aquí no hace falta.

-- 006_crear_usuario.sql create or replace function public.crear_usuario( p_email text, p_password text, p_nombre_completo text, p_cedula text default null, p_rol text default 'cajero' ) returns uuid language plpgsql security definer set search_path = public, extensions as $$ begin if not public.es_admin() then raise exception 'Solo un administrador puede crear usuarios'; end if; if exists (select 1 from auth.users where lower(email) = lower(p_email)) then raise exception 'Ya existe un usuario con ese correo'; end if; v_id := gen_random_uuid(); insert into auth.users ( id, email, encrypted_password, email_confirmed_at, raw_user_meta_data, ... ) values ( v_id, lower(p_email), crypt(p_password, gen_salt('bf')), now(), jsonb_build_object('nombre_completo', p_nombre_completo), ... ); insert into auth.identities (user_id, provider_id, provider, identity_data) values (v_id, v_id::text, 'email', jsonb_build_object(...)); -- el trigger crear_perfil() ya insertó la fila en perfiles update public.perfiles set rol = p_rol, nombre_completo = p_nombre_completo where id = v_id; return v_id; end; $$;

La barrera está en la base

Aunque alguien llame la función directamente, si no es administrador recibe la excepción. Probado: un cajero obtiene “Solo un administrador puede crear usuarios”.

Clave hasheada con bcrypt

crypt(clave, gen_salt('bf')) es el mismo algoritmo que usa Supabase. La clave nunca se guarda en texto plano.

Dos inserts obligatorios

Sin la fila en auth.identities el login por correo falla con error 500. Lo aprendimos probándolo.

El perfil se crea solo

El trigger crear_perfil() sobre auth.users inserta en perfiles con rol cajero por defecto.

El código en uso · 4

Del botón hasta la base de datos

El navegador nunca escribe SQL: llama una función o lee una tabla que el RLS le permite.

// 1) El cliente de Supabase en el servidor (src/lib/supabase/server.ts) export async function createClient() { const cookieStore = await cookies(); return createServerClient(url, key, { cookies: { getAll() { return cookieStore.getAll(); }, setAll(lista) { lista.forEach(c => cookieStore.set(c.name, c.value, c.options)); }, }, }); } // 2) La Server Action que registra la venta (src/lib/actions/ventas.ts) const { data, error } = await supabase.rpc('registrar_venta', { p_cliente_id: entrada.clienteId, p_metodo_pago: entrada.metodoPago, p_items: items, // solo producto_id y cantidad }); if (error) return { ok: false, mensaje: error.message }; // 3) La lectura en un Server Component const { data } = await supabase .from('productos') .select('*, categorias(id, nombre)') .eq('activo', true) .order('nombre');

La sesión viaja en cookies

@supabase/ssr guarda el token en cookies y proxy.ts lo refresca en cada petición. Así el servidor sabe quién es auth.uid().

RPC = llamar una función SQL

supabase.rpc('registrar_venta', …) ejecuta la función como el usuario autenticado: PostgreSQL aplica permisos y RLS.

Nunca se manda el total

El carrito calcula una vista previa para el usuario, pero el monto final lo calcula la función. Si el navegador manda un total, se ignora.

Errores de la base, al usuario

Si la función lanza “Stock insuficiente para X”, ese mensaje llega tal cual al toast del cajero.

Qué probamos y qué salió

No lo dimos por bueno “porque se veía bien”: se ejecutaron pruebas sobre una réplica y luego contra la base real.

Lo que se comprobó

  • El trigger crea el perfil al registrar
  • Un cajero no puede ascenderse a administrador
  • La numeración avanza FAC-000001, FAC-000002…
  • Vender sin stock lanza excepción y revierte todo
  • Anular devuelve el stock exacto
  • El cajero C no ve las ventas del cajero B
  • Borrar un producto vendido da error 23503
!

Dos cosas que descubrimos

1. Faltaban los GRANT. Las tablas existían pero la API devolvía 401 permission denied. Se agregaron los permisos para anon y authenticated (el RLS sigue filtrando).

2. Faltaba la identidad. Un usuario insertado solo en auth.users no podía entrar: el login daba error 500. Se aprendió que GoTrue también necesita auth.identities.

Se puede demostrar en vivo: pedir un usuario cajero y mostrar que en su sesión la lista de ventas viene vacía, y que al intentar anular recibe “Solo un administrador puede anular”.

Para cerrar

Tres ideas para recordar

1. La base de datos no es un almacén: valida, calcula y protege. El stock, el IVA y la numeración viven en PostgreSQL.

2. La seguridad no está en la interfaz: está en 13 políticas RLS y en funciones que verifican permisos por dentro.

3. Todo es reconstruible: seis archivos SQL en el repositorio levantan la base completa desde cero.
